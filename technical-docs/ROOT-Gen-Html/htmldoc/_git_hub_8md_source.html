1 # Using GitHub
2 
3 The way you use git and GitHub will depend on how you plan on interacting with the GRSISort code. If you plan on simply using the code, you should look at the User section. If you plan on developing the code (fixing issues or adding functionality), or just modifying the code for your own use, you should look at the Developer section.
4 
5 GitHub has a good [glossary](https://help.github.com/articles/github-glossary/) of commonly used terms.

7 ## User
8 
9 As a user, you will use git and GitHub to make sure that your local version (on your personal computer) is up-to-date with the online repository (on GitHub). The instructions for setting up your local version are well documented on the [[Setting Up GRSISort|Setting-up-GRSISort]] page.
10 
11 You'll probably want to stay abreast of all of the most recent GRSISort developments though. You can email notifications of updates by registering with GitHub and [“watching” the repository](https://help.github.com/articles/watching-repositories/), or you can just check from the command line. To check if there are any new updates to GRSISort from the command line, go to your GRSISort directory and type:
12 ```
13 git status
14 ```
15 You will get a long list of untracked files. These are all the libraries and binaries that you compiled when you typed make. Don't worry about these. DO go up to the top and look at the first few lines of the output. If it has output like this:
16 ```
17 OUTPUT THAT SAYS YOU ARE behind by so many commits...
18 ```
19 then you can update your version of GRSISort by typing:
20 ```
21 git pull.
22 ```

63 ## Developer
64 
65 As a developer, you will use git and GitHub to make sure your local version is up-to-date with the online repository, but you will also be modifying the code and potentially submitting changes to the online repository. To do this, you will need a more detailed understanding of git and GitHub. There are some resources online (see [here](http://rogerdudler.github.io/git-guide/) and [here](https://www.codeschool.com/courses/try-git), for example) that will be useful.
66 
67 ### Forking the common repository
68 The best path forward is to to create your own account on GitHub and [fork the repository] (https://help.github.com/articles/fork-a-repo/). This creates your own online repository that you can play with while not messing up the common repository. It also allows you to submit changes to the common repository. To do this, register with GitHub and then navigate to the GRSISort webpage. In the upper right-hand corner, click the “Fork” button. You should see your own version of this repository now.
69 
70 ### Downloading a copy of your personal repository
71 To install a local copy of your personal repository, follow the instructions in the [[Setting Up GRSISort|Setting-up-GRSISort]] page except instead of cloning `https://github.com/GRIFFINCollaboration/GRSISort.git`, clone `https://github.com/YOUR-USER-NAME/GRSISort.git`.
72 
73 ### Updating your code from the common repository
74 To this, you must first tell git where the upstream (common) repository is. This is succinctly and clearly explained in GitHub's [Configuring a remote for a fork](https://help.github.com/articles/configuring-a-remote-for-a-fork/) help page.
75 
76 The next step is to download the changes from the common repository. This is called [syncing a fork](https://help.github.com/articles/syncing-a-fork/). *(Advanced: check out the local branch you want to update first.)* To do this, use the following command:
77 ```
78 git pull upstream master
79 ```
80 This downloads (fetches) a copy of the changes (commits) from the common (upstream) repository. It also merges those commits into your own local copy of the code. If there are commits that conflict with changes you have made to your local repository, you will be asked to [resolve those conflicts](https://help.github.com/articles/resolving-a-merge-conflict-from-the-command-line/).
81 
82 The last step is to update your online repository. In executing the pull, you updated your local copy, but your personal repository still doesn't have these changes committed. To commit these updates to your local copy, use:
83 ```
84 git push origin master
85 ```
86 This pushes the changes from your local master branch to the online repository identified as origin. To see a list of the repositories you are connected to, use `git remote -v`.
87 
88 ### Making changes to your personal online repository
89 Add any files that you have created or modified to your staging area with:
90 ```
91 git add FILENAME1 FILENAME2 …
92 ```
93 Then update your online repository with the modifications specified in the staging area:
94 ```
95 git commit -m “Quick message that summarizes these changes.”
96 ```
97 If you do not use the `-m` flag, git will open up a text editor and ask you to write a commit message there. The point of this is to record exactly what changed and when – enforced documentation!
98 
99 Now that you have committed these changes to your local repository, you need to push them to your online repository:
100 ```
101 git push
102 ```
103 
104 If you see the error message:
105 ```
106 Error: The requested URL returned error: 403 while accessing
107 # https://github.com/user/repo.git/info/refs
108 # fatal: HTTP request failed
109 ```
110 or a similar message, check out [this](https://help.github.com/articles/https-cloning-errors/) help page and links within.
111 ### Suggesting a change to the common repository
112 To suggest a change to the common repository, first make sure your local copy has the most recent changes from the common repository. Then, update your personal online repository with the suggested changes. Finally, [create a pull request](https://help.github.com/articles/creating-a-pull-request/). An administrator will look over the code and merge it into the common online repository or discuss possible modifications to you proposed changes.
