14 # How To Use
15 -----------------------------------------
16 Effort has gone into ensuring that the `PROOF` framework is very easy to use for beginners still learning to use `ROOT`. For those interested in the `GRSIProof` code, the main program is located in the `GRSIProof` directory of `GRSISort`. PROOF uses the concept of a **selector** which is a class that knows how to process a single entry within a tree. In the context of `GRSISort`, this means either a single fragment, or a packaged event. First we will go through how and where to manipulate your own selectors for analysis.
17 ## Creating your own analysis selector <a name="create_script" />
18 There are examples of selectors in the `GRSIProof` directory. The more useful, and more complicated event selector (`ExampleEventSelector`) will be used as an example here. Everything is analogous for fragment files.
19 
20 The first thing that must be done is to change the class name. This must be done in both the `.C` and `.h` files within the `GRSIProof` directory. This must match the name of the scripts themselves! This also includes the namespace in front of every function. For example,
21 ```c++
22 void ExampleEventSelector::InitializeBranches(TTree* tree){
23 ```
24 Must become:
25 ```c++
26 void MyAwesomelyNamedSelector::InitializeBranches(TTree* tree){
27 ```
28 These **must be changed** in both the `MyAwesomelyNamedSelector.h` and the `MyAwesomelyNamedSelector.C`. You must ensure include files and `ifdef`s are correctly named as well.
29 ### Setting up detector classes
30 The detector systems you plan on analyzing using this script must also be declared in the `.h` file. For example, in `ExampleEventSelector`, there are lines of code with:
31 ```c++
32 TGriffin * fGriff;
33 TSceptar * fScep;
34 ```
35 A pointer to your detectors are setup at this point:
36 ```c++
37 TAwesomeDetector * fAwesomeDet;
38 ```
39 The code also needs to be told where to find the branch that contains your detector. This is done in the `.h` file in the function `InitializeBranches`. In our example, we would change
40 ```c++
41 tree->SetBranchAddress("TGriffin",&fGrif);
42 tree->SetBranchAddress("TSceptar",&fScep);
43 ```
44 to:
45 ```c++
46 tree->SetBranchAddress("TAwesomeDetector",&fAwesomeDet);
47 ```
48 
49 ### Change Output file name
50 This simple change can be done in the header file in the constructor of the selector. For example, the prefix of the file is changed by changing
51 ```c++
52 SetOutputPrefix("ExampleEvent");
53 ```
54 to:
55 ```c++
56 SetOutputPrefix("AwesomeSauce");
57 ```
58 For an analysis tree `analysis07654_002.root`, this would create an output root file called `AwesomeSauce07654_002.root`. You can put whatever you want for the prefix, it does not have to be related to the class name.
59 
60 ## Creating Histograms <a name="create_histos" />
61 The histograms are defined in the `.C` file in the function `CreateHistograms` (in our case `MyAwesomeSelector::CreateHistograms()`). We have setup a map that allows for easy access of histograms across various locations in the selector. This means to create a 1D histogram, one should use `fH1`, a 2D histogram in `fH2` etc. If the histogram type you want does not exist, please place a request on the issue tracker. As an example, the line:
62 ```c++
63 fH1["gE"] = new TH1D("gE","#gamma Singles",12000,0,3000);
64 ```
65 creates a 1D histogram with `double` precision called `"gE"` and puts it in a map position of `"gE"`. You do not need to match the name to the map position, but it is likely easier to keep track of things if you do this. The loops automatically add these histograms to the output root file using the lines:
66 ```c++
67 for (auto it: fH1) {
68  GetOutputList()->Add(it.second);
69 }
70 ```
71 These **must not** be changed.
72 
73 ## Filling Histograms <a name="fill_histos" />
74 To fill the histograms you just created, you can change the function located in the `.C` file named `FillHistograms` (in our case `MyAwesomeSelector::FillHistograms()`). You use the map to lookup the histogram you want to fill, and then fill it like a normal histogram. For example, to fill the 1D energy spectrum created above, we would loop over all `Awesome` hits, find the energy of the hit, and put it in our `"gE"` histogram.
75 ```c++
76 for(auto i = 0; i < fAwesomeDet->GetMultiplicity(); ++i){
77  fH1["gE"]->Fill(fAwesomeDet->GetAwesomeHit(i)->GetEnergy());
78 }
79 ```

81 ## EndOfSort <a name="end_of_sort" />
82 The EndOfSort function can be used to manipulated histograms after they have been filled.
83 By adding
84 ```c++
85 void EndOfSort();
86 ```
87 to the selectors header file and
88 ```c++
89 void <SelectorClassName>::EndOfSort() {
90 <code to manipulate histograms>
91 }
92 ```
93 to the selectors source file one can add code to create a background subtracted spectrum from a coincident and a time-random histogram, set bins to specific values, etc.
94 When setting bins to non-zero values, keep in mind that this happens before the histograms from the different slaves are merged, so the final value in the histogram will multiplied by the number of workers.

96 ## Running GRSIProof <a name="running" />
97 You run `grsiproof` as a separate program from GRSISort. The basic way to do so is:
98 ```bash
99 grsiproof root_file_to_sort.root location_to_selector.C
100 ```
101 for example:
102 ```bash
103 grsiproof analysis06578_000.root $GRSISYS/GRSIProof/MyAwesomeSelector.C
104 ```
105 a list of analysis files can be used and they will all be chained and sorted at the same time. This includes regular expressions. The output file name will be named after the first file in the list. For example:
106 ```bash
107 grsiproof analysis06578_000.root analysis06578_001.root analysis06578_002.root $GRSISYS/GRSIProof/MyAwesomeSelector.C
108 ```
109 would work and create a file called `AwesomeSauce06578_000.root`. One could also use:
110 ```bash
111 grsiproof analysis06578_???.root $GRSISYS/GRSIProof/MyAwesomeSelector.C
112 ```
113 to accomplish the same task.

115 ## Running Options <a name="running_options" />
116 There are options that can be provided on the command line to change the way `grsiproof` runs. Some options are listed below with what they do. A full list can be viewed with `grsiproof --help`.
117  * __--max-workers #__, Sets the number of slaves to be used. Each worker creates each histogram you create, so this is a good option to reduce memory consumption when using many histograms. Defaults to number of cores on computer.
118  * __--selector-only__, Bypasses proof, and just runs the selector on one thread. Good for debugging, as proof redirects output messages.
119 
120 [.info files](RunInfo-Files) can also be used. Their content is parsed as if it were normal command line arguments minus the dash(es) with the flag and the value separated by a colon.
121 This can be useful if multiple runs are to be analyzed in a single step, by listing all root-files with analysis trees (or fragment trees) in a .info file.
